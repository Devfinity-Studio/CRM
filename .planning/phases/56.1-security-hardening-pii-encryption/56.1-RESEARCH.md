# Phase 56.1: Security Hardening & PII Encryption - Research

## 1. PII Encryption Engine (AES-256-GCM)

### 1.1 Cryptographic Standard
- **Cipher:** `aes-256-gcm` built into Node.js `crypto`.
- **IV:** 12 bytes (96 bits) securely randomized via `crypto.randomBytes(12)` per encryption.
- **Tag:** 16 bytes (128 bits) authentication tag retrieved via `cipher.getAuthTag()`.
- **Ciphertext Serialization:**
  `enc:v1:${iv.toString("hex")}:${tag.toString("hex")}:${encrypted.toString("hex")}`
- **Benefits:**
  - Authenticated encryption prevents ciphertext tampering or bit-flipping attacks.
  - Prefix `enc:v1:` allows future key rotation schemes (v2, v3) and easy detection of whether a value is already encrypted or legacy plaintext.
  - Self-contained string fits comfortably within existing `varchar(50)` or `text` database columns.
  - Masking utilities (`XXXX-XXXX-1234` for Aadhaar, `XXXXX1234X` for PAN) allow safe frontend display without exposing plaintext numbers.

### 1.2 Integration Points in CRM
- Fields in `contacts`: `pan`, `aadhaar`, `passport`.
- Fields in `companies`: `businessPan`.
- When writing: Encrypt if non-empty string.
- When reading: Return decrypted value (for authorized viewers) alongside masked values for summary tables and cards.

## 2. Multi-Tenant Workspace Resolution Strategy

### 2.1 The Problem
In routers such as `billing`, `inventory`, `automations`, `apiKeys`, and `client-subscriptions`, every procedure queries:
```typescript
const member = await ctx.db.query.organizationMembers.findFirst({
  where: eq(organizationMembers.userId, ctx.session.user.id),
});
```
This fails when:
1. A user is a member of multiple organizations and switches workspaces in the UI.
2. A Super Admin impersonates an organization (`devcrm_impersonate_org` cookie), because the Super Admin has no `organizationMembers` row for that tenant.

### 2.2 Standardized Resolver Helper
In `src/server/api/trpc.ts`:
Create `resolveTenantContext(ctx, overrideOrgId?)`:
1. Check `ctx.impersonatedOrgId` (Super Admin impersonation cookie).
2. Check `overrideOrgId` or `ctx.headers.get("x-tenant-id")` or `ctx.session.user.organizationId`.
3. If an organization ID is specified:
   - If user is `SUPER_ADMIN`, grant access with role `SUPER_ADMIN`.
   - Otherwise, verify membership in `organizationMembers` for that `organizationId` and `userId`.
4. If not specified or user has no specific active tenant header:
   - Fall back to user's first membership in `organizationMembers`.
5. Return `{ organizationId, role, isOwner, isAdmin }`.
6. Throw `TRPCError({ code: "FORBIDDEN" })` if no valid tenant context is found.

## 3. Public Ingestion Hardening

### 3.1 `/api/leads`
- Validate payload with Zod schema (`organizationId`, `firstName`, `lastName`, `email`, `phone`).
- Verify target `organizationId` exists in `organizations` and `isActive` is `true`.
- Require authorization:
  Accept `Authorization: Bearer <api_key>` or `x-api-key: <key>`, or a valid signed workspace lead token.

### 3.2 `/api/webhooks/ads`
- Accept `x-ad-secret` header or webhook token.
- Verify against `process.env.AD_WEBHOOK_SECRET` (fail closed if invalid).

### 3.3 `publicRouter.submitQuoteRequest`
- Current vulnerability: Client submits `price` directly; backend sums `item.price * item.quantity` without validation.
- Fix:
  - Query DB `products` by `input.items.map(i => i.productId)`.
  - Use database `unitPrice` instead of client price.
  - Enforce `quantity >= 1`.
  - Calculate `totalAmount` strictly server-side.

## 4. Role-Based Access Control (RBAC)
- Mark sensitive procedures with an explicit role requirement:
  - `apiKeys.create` and `apiKeys.revoke`: Require `role === 'OWNER' || role === 'ADMIN'`.
  - `billing.deleteInvoice`, `billing.refundInvoice`: Require `role === 'OWNER' || role === 'ADMIN'`.
  - `webhooks.getAppPortalUrl`: Require `role === 'OWNER' || role === 'ADMIN'`.
