# Phase 56.1: Security Hardening & PII Encryption - Context

## 1. Phase Overview
- **Phase Number:** 56.1 (Inserted Urgent Milestone 19 Phase)
- **Goal:** Implement application-level PII encryption (PAN, Aadhaar, Passport), eliminate cross-tenant IDORs and stale workspace resolution in remaining domain routers (`billing`, `inventory`, `automations`, `apiKeys`, `clientSubscriptions`), secure public ingestion endpoints (`/api/leads`, `/api/webhooks/ads`, `public.submitQuoteRequest`), and enforce RBAC for destructive actions.
- **Predecessor:** Phase 56 (Dynamic Feature Flags & Cascading Module Toggles)

  1. Cryptographic AES-256-GCM envelope encryption utility with secure key derivation, IV, and auth tag for `pan`, `aadhaar`, and `passport` fields.
  2. Safe contact retrieval in `crmRouter` supporting decryption for authorized viewers and masked display values (`XXXX-XXXX-1234`).
  3. Consistent active organization resolution across `billing`, `inventory`, `automations`, `apiKeys`, and `clientSubscriptions` (eliminating stale first-membership bugs and supporting Super Admin impersonation).
  4. Secured public lead and ad webhook endpoints with token authentication, payload schema validation, and server-side product price verification in `public.submitQuoteRequest`.
  5. Destructive actions restricted to `OWNER` and `ADMIN` roles.
  6. 100% of Vitest unit tests passing and clean Next.js production build (`pnpm build`).

## 2. Key Architecture Decisions

### 2.1 Cryptographic Envelope Encryption for PII
- **Algorithm:** AES-256-GCM (Authenticated Encryption with Associated Data).
- **Format:** `enc:v1:<iv_hex>:<auth_tag_hex>:<ciphertext_hex>`.
- **Key Source:** `ENCRYPTION_SECRET` (derived or loaded from environment, with deterministic 32-byte hash fallback in development/test).
- **Masking:** Provide `maskAadhaar(str)`, `maskPan(str)`, `maskPassport(str)` utility functions for frontend display.

### 2.2 Multi-Tenant Workspace Resolution
- Domain routers currently invoke:
  `const member = await ctx.db.query.organizationMembers.findFirst({ where: eq(userId) })`
  which ignores active workspace switching and breaks Super Admin impersonation.
- **Resolution Strategy:**
  Standardize with a shared helper `resolveActiveOrgId(ctx)` that checks:
  1. `ctx.impersonatedOrgId` (Super Admin impersonation cookie)
  2. `ctx.session.user.organizationId` (API Key or JWT active org)
  3. `ctx.headers.get("x-tenant-id")` or `x-tenant-slug`
  4. Verified user membership in target organization (or `SUPER_ADMIN` bypass)
  5. Fallback to first membership if none specified.
- Ensure all queries scope explicitly to this verified `activeOrgId`.

### 2.3 Public Ingestion Hardening
- `/api/leads`: Validate required fields with Zod, verify organization exists and is active, and require a valid workspace API key or token header.
- `/api/webhooks/ads`: Require `x-webhook-secret` matching `process.env.AD_WEBHOOK_SECRET` (or fail closed in production).
- `publicRouter.submitQuoteRequest`: Cross-reference `productId` against database `products` to compute total amounts server-side, preventing client price manipulation and enforcing positive quantities (`min(1)`).

### 2.4 Destructive RBAC
- Actions modifying organization credentials, deleting invoices, issuing credit notes, or modifying webhooks require `ctx.tenant.role === 'OWNER'` or `'ADMIN'` (or `systemRole === 'SUPER_ADMIN'`).
